# Bounded Tool-Calling Agent

## Scope

A single analytics assistant answers questions about historical Capital Bikeshare activity using locally executed, validated Python tools. It supports Gemini through the Google GenAI SDK and Groq through its OpenAI-compatible chat-completions interface. The system does not grant either model unrestricted SQL, filesystem or Python access.

## Configuration

Provider priority is controlled through `AGENT_PRIMARY_PROVIDER=groq` or `gemini` in the untracked `.env`. The supplied template uses Groq first because the project has observed Gemini HTTP 400 errors; Gemini can still be attempted on a Groq API failure if a key is configured. Model IDs are set with `GROQ_MODEL` and `GEMINI_MODEL`.

```dotenv
AGENT_PRIMARY_PROVIDER=groq
GROQ_API_KEY=your_groq_api_key
GROQ_MODEL=openai/gpt-oss-120b
GEMINI_API_KEY=your_optional_gemini_key
GEMINI_MODEL=gemini-3.5-flash-lite
```

Model access and quotas depend on the provider and project. Never commit credentials or send private data through this public-data demo.

## Execution flow

1. Validate the question (nonempty string of at most 2,000 characters) and resolve the selected provider.
2. Supply the model with six fixed tool declarations and a system instruction requiring evidence-backed numerical claims.
3. Read each model-requested function call and pass it through `src.agent_tools.dispatch_tool()`. The dispatcher validates the allowlist and strict argument contract before executing any function.
4. Return the structured result using Gemini's function-response parts or Groq's matching `tool_call_id` messages.
5. Repeat until the model returns a textual answer, or the limit is reached.
6. Only on provider API failure, start a new, independent conversation using the alternate provider. Do not fall back for model text, ordinary tool failures or exhausted tool rounds.

Each provider attempt is bounded to four tool rounds and eight total calls. A final model response can require an additional API request. Local functions are read-only, making provider-restart duplication safe within the current tool set.

## Grounding

The model must distinguish historical SQL statistics from conditional XGBoost estimates. Each historical statement should include its units and relevant sample size. The `compare_workdays` analytics function supplies two deterministic fields on the working-day row: the absolute difference and the percentage difference versus the non-working-day hourly mean. The system instruction directs the language model to use the computed percentage rather than performing mental arithmetic; this mitigates but does not guarantee against numerical errors.

The source covers 2011–2012. No current-demand forecast, causal assertion, station-level operational recommendation or live inventory claim can be justified from these tools.

## Application interface

`app.py` exposes a conversational analytics tab using `gr.ChatInterface`. **Chat history is displayed but not included in requests to the model**. Each question is independently interpreted; users must restate context in follow-ups. The prediction form and historical profile chart are separate, deterministic application functions.

## Verification

```bash
python -m pytest -q
python -m scripts.agent_smoke_test
python app.py
```

Tests mock provider responses and validate local control flow. A live smoke test confirms connectivity and a representative tool-calling response, but further manual checks are needed to identify any factual, arithmetic or formatting mistakes generated by the model.
